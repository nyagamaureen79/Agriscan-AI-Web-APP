# Sharing `agriscan_db` with the mobile app

The mobile app's Django backend uses this same database. It owns every table prefixed `agriscan_`, plus Django's `auth_*` and `django_*` tables. It reads, and for mobile farmers writes, some web tables: `FarmerRegistration`, `FarmProfile`, `CropProductionData`, `financialentries`, `Feedback` and `ImageScan`.

## What this branch changes

- **Migration `a3c9e1f2d4b6`** adds `FarmerRegistration.firebase_uid` (`varchar(128)`, nullable, unique index `ix_FarmerRegistration_firebase_uid`). The mobile backend writes the Firebase uid there, so web and mobile resolve a farmer to the same row. The migration is idempotent.
- **`alembic/env.py` guards the mobile tables.**
  - `include_name` never reflects `agriscan_*`, `auth_*` or `django_*` tables.
  - `include_object` never proposes dropping a table that exists in the database but has no model here.

  Without these guards, `alembic revision --autogenerate` against a copy of production proposed 100 `drop_table`s: 67 mobile tables and 33 web tables that are read without a model. With them it proposes none.
- **`env.py` imports every module in `app/models`**, not just `users` and `tenants`. `EntryCategory`, `payments` and `payment_transactions` were missing from the metadata.
- **Model fixes that autogenerate needed in order to run at all:**
  - `financialentries` foreign keys now name `FarmerRegistration` and `EntryCategory`, not the lower-case spellings. The database is case-sensitive.
  - `String` columns without a length got the live types: `FarmerRegistration.password` `String(255)`; `payments.invoice_id`/`status`/`payment_method` `255`/`50`/`100`; `SequestrationType.description` `Text`.

  None of these change the database.

## Deploying: order matters

Production's `alembic_version` is empty even though the schema is at `1b1fb8bde557`, so a bare `upgrade head` would try to re-create `users`.

```sh
alembic stamp 1b1fb8bde557
alembic upgrade head        # applies a3c9e1f2d4b6
# then deploy this code
```

Deploy the code **after** the migration. Startup `create_all` never adds columns, so a model that maps `firebase_uid` would query a column that doesn't exist yet.

## Still true after this branch

- **Review every autogenerated migration.** Autogenerate still reports older drift between the models and the web's own tables: about 34 column drops, 83 column alterations and index changes. None of these touch mobile tables, but applying them unreviewed would change the web's schema.
- **Don't rename or drop** a `FarmerRegistration`, `FarmProfile`, `CropProductionData`, `financialentries`, `systemcodedetails`, `tenants` or `document_chunks` column without telling the mobile team. Their backend refuses to start on a schema it doesn't recognise.
- **Any other branch that adds `firebase_uid`** (for example a revived `feat/mobile-vertex-gemini-chat` with migration `8e5f6a7b9c10`) must be re-parented onto `a3c9e1f2d4b6`, with its duplicate column and index removed. Otherwise there will be two heads.
